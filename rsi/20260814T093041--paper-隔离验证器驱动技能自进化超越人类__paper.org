#+title:      隔离验证器驱动技能自进化超越人类
#+subtitle:   CoEvoSkills: Self-Evolving Agent Skills via Co-Evolutionary Verification (COLM 2026)
#+source:     https://arxiv.org/abs/2604.01687
#+authors:    Hanrong Zhang, Shicheng Fan, Henry Peng Zou, Yankai Chen, et al.
#+venue:      COLM 2026

* 速读

Anthropic 提出的 agent「技能」（skill）是比工具更复杂的结构——一组多文件的工作流指令、可执行脚本和领域参考。
但现在技能全靠人写，费时且会因「人机认知错位」拖后腿：在 SkillsBench 上，人类精心编写的技能在自然科学领域反而降低了 agent 表现。
CoEvoSkills 的核心发现是：技能质量的瓶颈不在生成而在验证——一次性生成的技能和不写技能几乎一样差，全部增益来自一个信息隔离的验证回路。
具体做法是用一个独立 LLM 会话充当「代理验证器」，自行合成测试、给出结构化失败诊断，但永远看不到真值测试内容；
当代理测试全过但真值 oracle 失败时，只回传一个 pass/fail 比特，逼迫验证器自己升级测试。
这个双回路在 5 轮内让 pass rate 从 32% 升到 75%，最终 71.1%，超过人类技能 17.6 个百分点，还能跨 6 个模型迁移。
以后看到 agent 技能效果不好，先问它编码的是 agent 原生推理模式还是人类假设，再问有没有验证回路在驱动迭代。

* 它到底在解决什么

一个具体的困惑：SkillsBench 给系外行星凌星周期检测任务配备了 5 份人类技能文档，共 1,096 行，把 BLS、TLS、Lomb-Scargle 三种算法平等列出，让 agent 自己选。
agent 用这些技能，表现没有提升。人类专家觉得「列出选项让 agent 自己判断」是直觉上合理的写法，但 agent 不知道该选哪个，也无法从 246 行文档的两行提示里推断出需要两阶段精度搜索。

这不是个例。SkillsBench 的评测显示，人类编写的技能在 11 个领域中的某些领域（如自然科学）会主动降低 agent 性能。
作者将此归因于「人机认知错位」：为人类专家设计的直觉工作流和抽象层次，不匹配 LLM 在执行约束下处理上下文、推理和行动的方式。

现有的自动化方法帮不上忙。它们面向的是「工具」——单一的、自包含的函数——而不是「技能」这种多文件结构化包。而且有些方法（如 EvoSkill）需要真值答案来做失败诊断，在真实场景里拿不到。
一次性生成多文件技能包本身也极不可靠：论文的数据显示，不管用什么生成策略（裸生成、CoT 引导生成、Anthropic 官方 skill-creator），一次性生成的技能几乎不比没有技能好——pass rate 都在 30-34% 之间徘徊，和无技能基线 30.6% 基本持平。

问题的本质是：没有真值反馈，agent 怎么知道生成的技能哪里错了？

* 它真正看见了什么

一句人话：**技能自进化的瓶颈是验证不是生成；一个信息隔离的代理验证器可以在不看真值的情况下提供密集反馈，驱动技能质量持续上升。**

机制是一个双回路协同进化结构。Skill Generator 维护一个持久对话上下文，迭代修订技能包。
Surrogate Verifier 是一个独立 LLM 会话——它看不到生成器的推理过程、技能源码或真值测试内容——只从任务指令、可观测输入和产出物出发，自行合成确定性测试断言，计算代理奖励。

两个回路的关键区别在于反馈的密度和信息的隔离：

#+begin_example
 ┌─── 内循环：代理验证器未通过 (R̃ < 1) ──────────────────┐
 │                                                        │
 │  Generator ──S──▶ 执行E ──y──▶ Surrogate Verifier     │
 │      ▲                                   │             │
 │      └──── 密集诊断F(根因+修复建议) ◀────┘             │
 └────────────────────────────────────────────────────────┘

 ┌─── 外循环：代理通过但真值未通过 (R̃=1, R<1) ────────────┐
 │                                                        │
 │  Verifier ──R̃=1──▶ Oracle ──pass/fail(1bit)──▶ Verifier│
 │     ▲                                              │    │
 │     └──── 升级测试 V (更多/更难的断言) ◀───────────┘    │
 └────────────────────────────────────────────────────────┘
  信息隔离：验证器永远看不到真值测试内容，只收到 1 个 bit
#+end_example

内循环提供密度：代理验证器失败时，它给出每个断言的通过/失败、根因分析和可执行的修复建议，直接喂回生成器。
外循环制造压力：当代理测试全过但真值 oracle 失败时，生成器只收到一个不透明的 pass/fail 比特——拿不到任何测试内容或失败细节——这防止了生成器过拟合到真值测试。
但这个比特触发验证器自己升级测试（更多样、更全面、更有挑战性），形成协同进化的军备竞赛。

这个设计最精妙的地方在于信息隔离的层次：代理验证器既看不到真值测试内容，也看不到生成器的推理过程。它只能从可观测的任务输入和产出物推断测试。
这意味着代理测试永远是真值测试的一个不完美近似——但正是这个「不完美」是安全的，因为生成器无法通过代理验证器偷看真值。

**关键证据一：验证回路而非生成提示是质量的唯一来源。** 消融实验显示，去掉代理验证器（生成器仍迭代 5 轮，但只用 1-bit oracle 信号），pass rate 从 71.1% 暴跌到 41.1%（-30pp）。
去掉整个进化回路只保留背景上下文，降到 42.4%。而一次性生成——无论裸生成、CoT 引导还是 Anthropic 官方 skill-creator——全在 30-34% 之间，和没有技能一样。
这个结果在这些条件下较稳地显示：没有结构化诊断反馈，生成器无法做有针对性的修复，迭代是低效的。

**关键证据二：协同进化驱动了算法层面的质变，不只是参数微调。** 论文附录的系外行星检测案例完整展示了这一点：

#+begin_example
 轮次  代理验证器      真值Oracle    关键事件
 1     0/15 (0%)       —            初始技能有 bug
 3     15/15 (100%)    3/4 (75%)    精度不够(BLS网格太粗)
 4     20/20 (100%)    3/4 (75%)    精度修了，别名检测失败
 5     19/22 (86%)     —            代理验证器抓到回归
 6     22/22 (100%)    4/4 (100%)   全部通过
#+end_example

前三个版本一直在 BLS 框架内调参数（去趋势方法、搜索范围），真值 oracle 连续两次返回 75%。直到第三轮 75% 反馈后，agent 认识到「在 BLS 内调参数无法达到 5 位小数精度」，
第四版直接把算法从 BLS 换成 TLS（凌星最小二乘法），加了 Savitzky-Golay 滤波和两阶段搜索，一步到 100%。这个算法替换的决策是被真值 oracle 的反复 75% 反馈逼出来的，
代理验证器的功能测试无法发现这个数值精度天花板。

这个案例还暴露了代理验证器的结构性局限——即「代理-真值鸿沟」：第 3 轮代理验证器 15/15 全过，但真值只有 75%，因为代理验证器无法推断出 5 位小数的精度阈值。
到第 5 轮，代理验证器升级到 22 个测试并加了 BLS 交叉验证，反而误判了 agent 更准确的 TLS 结果（差 0.00002 天）。
这说明代理验证器不能替代真值 oracle，但它在进化早期吸收了大量迭代成本——平均 4.1 个验证周期中只有 2.4 个升级到真值 oracle。

**跨模型迁移**进一步验证了技能编码的是任务结构而非模型特定产物。
用 Claude Opus 4.6 进化的技能迁移到 6 个来自 5 家公司的模型上，每个模型相对各自的无技能基线提升 35-44 个百分点。
GPT-5.2 自己进化的技能（69.8%）比 Opus 迁移过来的（65.0%）好 4.8pp，说明模型匹配的进化有微弱优势，但迁移后的技能仍然大幅超越基线。

适用边界：这些结果在 SkillsBench 的 85 个任务上取得，覆盖 11 个专业领域。技能进化的起点是初始化时可用的任务相关背景知识（文档、领域参考），不是从零开始。
论文承认开放世界技能进化——agent 自主寻找和验证初始任务上下文之外的知识——是下一步工作。

* 我能带走什么

以后看到 agent 技能效果不好（尤其是人类精心编写却不见提升甚至降低性能），先不急着判断「技能没用」或「模型不够强」，而会先问两个问题：
这个技能编码的是 agent 实际需要的推理模式和工具使用策略，还是人类专家对 agent 应该怎么操作的假设？
驱动技能迭代的是一个有结构化诊断反馈的验证回路，还是只有一次性生成加一个不透明的 pass/fail？

一个直接相关的用法：在构建 agent 的自我改进系统时，把改进对象从「提示词」或「单一工具」扩展到「多文件技能包」，并用一个信息隔离的代理验证器替代真值反馈。
信息隔离的关键不是隐藏答案本身，而是只回传 1 个比特——这逼着验证器自己升级测试，而不是把真值测试内容泄露给生成器导致过拟合。
