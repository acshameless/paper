#+title: 动态组合性即运行时效应与协效应
#+subtitle: A Programming Paradigm for Spatiotemporal Composability
#+source: [[pdf: D:/download/paper.pdf]]
#+authors: Yifan Shi, Wei Zhang, Tianyi Cui
#+venue: Peking University / DeepSeek-AI

* 速读

这篇论文做了一件什么事？它把类型论里两个成熟的工具——效应系统（effects）和协效应系统（coeffects）——从编译期搬到了运行时，用来解决动态组合（运行时加载、卸载、替换组件）的两个核心难题：卸载一个组件时怎么撤销它做过的一切（时间维度），组件之间怎么声明和管理依赖关系（空间维度）。

论文给出了完整的形式化模型（可逆效应 + 反应式协效应 + 统一上下文类型）、一套演算规则（10 条，含 3 条编排规则和 7 条生命周期规则）、元理论证明（保持性、恢复精确性、合流性）、以及一个叫 Cordis 的实现和 Koishi 聊天机器人框架的案例验证（4000+ 社区插件）。

* 它到底在解决什么

** 动态组合的两个痛点

你写了一个插件系统，比如 VSCode 的扩展生态。用户装了上百个扩展，每个扩展都会往编辑器里注册命令、改快捷键、加 UI 元素。现在用户要卸载其中一个扩展——你能把它做过的事情全部撤销吗？

论文调查了 VSCode 排名前 100 的扩展，发现 87 个包含可执行代码，而插件系统无法在不重启的情况下卸载它们的副作用。只有 7 个声明了依赖关系。这意味着：卸载靠开发者自觉写清理代码（很多人不写），依赖管理靠用户自己猜（系统不管）。

这不是 VSCode 独有的问题。Erlang 热更新靠手写状态迁移函数，OSGi 靠开发者写 deactivate 回调，React 的 useEffect 靠组件返回 cleanup 函数。所有这些方案有一个共同特征：*组合性是开发者的纪律，不是系统的保证*。

** 两个维度

论文把动态组合拆成两个正交维度：

- *时间维度（temporal）*：卸载一个组件时，能不能把它对系统做过的所有修改全部回滚？这要求每个操作都有一个逆操作，且运行时能追踪和执行这些逆操作。
- *空间维度（spatial）*：组件之间能不能声明依赖关系，且当依赖变化时系统能自动响应？这要求组件声明自己需要什么，运行时在依赖满足或消失时自动激活或停用组件。

现有方案要么只解决一个维度，要么两个都靠开发者自觉。论文要同时解决两个，且让它们成为结构保证。

* 它真正看见了什么

** 关键洞察：两个维度就是效应与协效应

论文最核心的判断是：*动态组合的时间维度和空间维度，恰好对应类型论里的效应（effects）和协效应（coeffects）*。

效应描述一个计算"做了什么"（修改了什么状态），协效应描述一个计算"需要什么"（依赖什么上下文）。这两个概念在类型论里已经成熟了几十年，但一直是编译期的工具——编译器用它们检查类型安全，运行时不管。

论文说：把它们从编译期搬到运行时，组合性就变成了结构保证。

** 可逆效应：每个操作自带逆操作

时间维度的解法是"可逆效应"（revertible effects）。经典效应系统记录"这个操作修改了状态"，但不关心怎么撤销。可逆效应要求：每个对上下文的修改都附带一个逆操作，运行时自动追踪这些逆操作，在组件卸载时按后进先出顺序执行它们。

这跟 React 的 useEffect 返回 cleanup 有形似之处，但有关键区别：useEffect 的 cleanup 只能在组件顶层调用、不能在条件/循环/嵌套函数里用、不能是 async。Cordis 的效应是普通操作，自由组合，且只需要为每个原子操作写逆操作——复合操作的逆操作由组合自动推导出来。

** 反应式协效应：声明依赖，运行时通知

空间维度的解法是"反应式协效应"（reactive coeffects）。经典协效应系统在编译期检查"这个计算需要什么上下文"。反应式协效应把它搬到运行时：组件声明自己需要哪些键（coeffect specification），运行时在上下文变化时检查这些声明，把变化分类为激活、停用或中性，然后自动触发对应的生命周期转换。

一个组件的依赖不可用时，它就保持非活跃状态，不报错；依赖出现时，它自动激活。提供者被替换时，依赖者自动重新加载。这一切由运行时管理，不需要开发者编排加载顺序。

** 统一上下文类型

论文把效应上下文和协效应上下文统一成一个递归类型，让效应和协效应在同一个结构里共存。关键是一个叫"观察等价"（observational equivalence）的概念：两个状态如果没有任何观察者能区分，就是等价的。这个等价关系让不同组件的效应互相独立——一个组件的修改不会意外影响另一个组件的逆操作。

** 演算与元理论

论文给出一套完整的演算规则（10 条），把组件、纤维（fiber，组件的运行时实例）、注册表组织成一个形式系统。三条编排规则管组件的插入、退休、移除；七条生命周期规则管组件的激活、迭代、完成、转移、离开、卸载、异常。

元理论证明了三个关键性质：

- *保持性*：每步操作保持系统良构
- *恢复精确性*：卸载一个组件后，上下文精确回到它加载前的状态
- *合流性*：不管你以什么顺序加载和卸载组件，最终静止状态等价于按依赖顺序一次性加载的静态组装结果

合流性是最强的保证：它意味着你可以把一个动态演化的系统当作静态组装的系统来推理。

* 我能带走什么

** 组合性应该是系统的不变量，不是开发者的纪律

这篇论文最大的启发不是某个具体技术，而是一个设计原则：*如果你发现组合性靠开发者自觉，那说明你的抽象层缺了一块*。VSCode 的插件卸载问题、OSGi 的 deactivate 回调遗忘问题、React useEffect 的限制问题，本质上都是同一个缺失：系统没有追踪效应的逆操作。

Cordis 的做法是：所有上下文修改都通过一个原语（ctx.effect）走，这个原语自动追踪逆操作并组合它们。开发者只需为每个原子操作写逆操作，复合操作的逆操作由系统自动推导。这让"完整恢复"成为系统不变量而非开发者责任。

** 效应和协效应不只是类型论工具

类型论里的效应和协效应一直被视为编译期的静态分析工具。这篇论文展示了：把它们提升到运行时，能解决一类全新的问题——动态组合。这个思路可以启发其他领域：还有哪些编译期的类型论工具，搬到运行时后能产生新的结构保证？

** 对自进化 Agent 框架的直接启示

论文在结论里特别提到自进化 Agent 框架（self-evolving agent harnesses）作为未来验证方向。AI Agent 持续生成和替换自己的组件，这恰好是动态组合的极端场景：高频替换、拓扑频繁变化、几乎无人工监督。Cordis 的可逆效应保证组件替换时完整恢复，反应式协效应保证依赖拓扑变化时自动协调。这为 Agent 自进化提供了一个可能的形式化基础。

** 系统边界是诚实的

论文没有假装能撤销一切。它明确区分了"边界内"（系统独占且可恢复的位置）和"边界外"（其他进程也能访问的位置）。边界内的操作可逆，边界外的操作不可逆。对于边界外的操作（比如发了一个网络请求），论文提供了两种策略：延迟提交（withhold）和补偿（compensation，比如退款）。这种诚实让理论不至于过度承诺。
