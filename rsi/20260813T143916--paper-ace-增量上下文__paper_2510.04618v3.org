#+title:      上下文要增量积累，不要整体重写
#+subtitle:   Agentic Context Engineering: Evolving Contexts for Self-Improving Language Models (ACE)
#+source:     https://arxiv.org/abs/2510.04618v3
#+authors:    Qizheng Zhang, Changran Hu, Shubhangi Upasani, Boyuan Ma, Fenglu Hong, Vamsidhar Kamanuru, Jay Rainton, Chen Wu, Mengmeng Ji, Hanchen Li, Urmish Thakker, James Zou, Kunle Olukotun
#+venue:      ICLR 2026

* 速读

LLM 系统在迭代中让模型重写自己的上下文（指令、策略、记忆）时，会发生"上下文崩塌"——一步之内 18K token 压成 122 token，积累的知识被抹掉，性能跌到不如不做任何适配。
ACE 看见的原因是整体重写：让 LLM 每步重新生成整个上下文，它倾向于越写越短。
解法是把上下文拆成结构化条目，只做增量 delta 更新——Reflector 从执行轨迹抽取新教训，Curator 只写新条目，用确定性逻辑合并进已有 playbook，绝不重写整体。
在 AppWorld agent 基准上，ACE 用更小的开源模型追平了 GPT-4.1 驱动的生产级 agent；消融实验显示去掉增量更新，增益几乎归零。
以后看到 LLM 系统在迭代中重写自己的上下文或记忆，先问的不是"重写质量够不够好"，而是"这次重写会不会把积累的知识抹掉"。

* 它到底在解决什么

一个 LLM agent 在 AppWorld 上跑任务，到第 60 步时，它的上下文已经积累了 18,282 token 的策略和教训，准确率 66.7%。
但到第 61 步，模型被要求重写整个上下文——它把 18K token 压缩成了 122 token，准确率暴跌到 57.1%，比完全不用适配的基线（63.7%）还差。作者把这种现象叫"上下文崩塌"（context collapse）。

这不是个例。现有的上下文适配方法有两个系统性缺陷：

1. *简洁偏置*（brevity bias）：提示优化器（如 GEPA）倾向于把指令压缩成简短通用的摘要，丢掉领域特定的启发式规则、工具用法细节和常见失败模式。
2. *上下文崩塌*（context collapse）：依赖 LLM 整体重写上下文的方法（如 Dynamic Cheatsheet），随着上下文变大，模型倾向于把它压成更短、信息更少的摘要，积累的知识被突然抹掉而非保留。

这两个缺陷的根源是同一个假设：上下文应该被压缩成简洁摘要。但在 agent 和知识密集型推理场景中，成功恰恰依赖于保留详细的、领域特定的知识，而不是压缩它。
人类受益于简洁概括，但 LLM 在长上下文下能自行蒸馏相关性——给它详细上下文，比给它压缩后的摘要更有效。

* 它真正看见了什么

新判断：上下文不是待压缩的摘要，而是一本活的手册（playbook）——它应该只增不改，通过增量更新积累策略，而不是每步重写整体。

ACE 用三个专职角色实现这个原则：

#+begin_example
  整体重写（DC 等）：
    Playbook(18K tok) ──LLM 重写──→ Playbook(122 tok)  ← 知识被抹掉
    每步重新生成整个上下文 → 越写越短 → 崩塌

  增量更新（ACE）：
    Playbook(bullets) ──┬── Reflector 从轨迹抽取新教训
                        └── Curator 生成 delta bullet ──→ 确定性合并
    只加/改具体条目，不碰其余 → 积累不丢失
#+end_example

三个角色的分工：

- *Generator*：用当前 playbook 执行任务，产生推理轨迹；同时标记哪些已有条目有用、哪些有误导。
- *Reflector*：分析轨迹，诊断成功和失败的原因，抽取可复用的教训。可多轮迭代精炼。
- *Curator*：把教训压缩成紧凑的 delta 条目，用轻量确定性逻辑（非 LLM）合并进已有 playbook。

上下文被表示为结构化条目（bullet）的集合，每个条目有唯一 ID、有用/有害计数器和内容。更新时只追加新条目或更新已有条目的计数器，再通过语义嵌入做去重。这避免了整体重写的计算成本和信息丢失，同时支持并行批量合并。

关键证据：

1. *增量更新是核心机制*。
消融实验中，去掉增量更新（退回整体重写），AppWorld test-normal 平均准确率从 70.3% 跌到 56.9%——增益几乎归零。这说明 ACE 的提升不主要来自三角色架构本身，而来自"不重写整体"这个设计。

2. *用更小模型追平生产级 agent*。
在 AppWorld 排行榜上，ACE + DeepSeek-V3.1（开源模型）在线适配后达到 59.5% 平均分，追平排名第一的 IBM CUGA（60.3%，用 GPT-4.1）。
在更难的 test-challenge 上，ACE 在线适配甚至超过 IBM CUGA 8.4 个点（TGC）。这较稳地显示，增量上下文积累能让较小模型达到大模型生产级 agent 的水平。

但有一个重要边界：ACE 的效果依赖反馈信号质量。在有执行反馈（如代码执行成功/失败）或 ground-truth 标签时，ACE 稳定提升；
但在没有可靠反馈信号的领域任务上，Reflector 可能抽取到虚假或误导性教训，污染上下文，导致性能下降。
论文也诚实报告了这一点——在 FiNER 在线适配无标签设置下，ACE 比 base LLM 低 3.4 个点。这说明 ACE 不是无条件有效的，它需要可靠的反馈来源。

* 我能带走什么

以后看到 LLM 系统在迭代中重写自己的上下文或记忆，先不急着判断"重写质量够不够好"，而先问"这次重写会不会把之前积累的知识抹掉"。如果会，改用增量更新：只追加新条目，不重写整体。

一个相关用法：在设计 agent 记忆系统时，把记忆拆成带 ID 的条目，用确定性逻辑做合并和去重，而不是让 LLM 每次重新总结全部记忆。
另一个用法：评估上下文适配方法时，除了看准确率，还要看上下文在长周期内是否稳定增长——如果 token 数在某步突然骤降，说明发生了崩塌，即使短期指标还行，长期也会退化。
