#+title:      协同进化验证环才是技能质量驱动力
#+subtitle:   CoEvoSkills: Self-Evolving Agent Skills via Co-Evolutionary Verification
#+source:     https://arxiv.org/abs/2604.01687
#+authors:    Hanrong Zhang, Shicheng Fan, Henry Peng Zou, Yankai Chen, Zhenting Wang, Jiayu Zhou, Chengze Li, Wei-Chieh Huang, Yifei Yao, Kening Zheng, Xue (Steve) Liu, Xiaoxiao Li, Philip S. Yu
#+venue:      COLM 2026

* 速读

人类手写的 agent 技能在某些领域（如自然科学）反而降低性能，而让 agent 一次性自生成技能也几乎无效——无论加 CoT 引导还是用 Anthropic 官方 skill-creator，都只停在 30-34%，跟没有技能的基线差不多。
CoEvoSkills 发现技能质量的主要驱动力不是生成提示词，而是一个信息隔离的协同进化验证环：
生成器与独立验证器互相施压——验证器在代理测试全通过但真值测试失败时被迫升级测试，生成器在验证器的结构化诊断驱动下做定向修复。
5 轮内通过率从 32% 升到 75%，超过人类手写技能（53.5%），且生成的技能能跨 6 个模型迁移。以后构建 agent 技能时，先问的不是「生成质量如何」，而是「有没有一个独立于生成器的验证回路在持续施压」。

* 它到底在解决什么

SkillsBench 评测发现了一个反常现象：人类专家精心手写的 agent 技能，在自然科学领域反而让 agent 性能下降。
这不是个例——人类按自己的直觉组织工作流，但 agent 处理上下文、推理和执行的方式跟人不同（human–machine cognitive misalignment）。
人类觉得「先列三种算法再选」很自然，agent 却在三个等价选项间犹豫；人类写「refine candidates」只需一句话，agent 不知道该细化到什么精度。

那让 agent 自己生成技能呢？也不行。无论用 CoT 引导的五步生成、还是 Anthropic 官方 skill-creator，一次性自生成的技能都只停在 30-34%，跟没有技能的基线（30.6%）几乎没有区别。
问题不在于 agent 不会写技能，而在于生成之后没有反馈——生成器不知道自己写的技能哪里有 bug、哪里逻辑不通。

现有自进化方法（Voyager、EvoSkill 等）只能处理单文件工具函数，无法应对多文件技能包。更要命的是，有些方法（如 EvoSkill）依赖真值答案来诊断失败，在真实场景中根本拿不到这种监督信号。

* 它真正看见了什么

技能质量的主要驱动力不是生成提示词，而是协同进化验证环。

CoEvoSkills 把「生成」和「验证」拆成两个信息隔离的 LLM 会话，让它们交替施压。Skill Generator 维护持久对话上下文，生成和修复技能；
Surrogate Verifier 是一个完全独立的会话，看不到生成器的推理过程和技能源码，只看任务指令和执行产出，自行合成测试断言。

关键在于两条反馈路径的交替触发：

#+begin_example
  Generator ──生成S──► 执行 ──► artifacts
     ▲                                │
     │ 诊断F(失败用例+根因+修复建议)    │
     │                                ▼
     │                      Surrogate Verifier(独立会话)
     │                       生成测试V, 评估artifacts
     │                                │
     │                   ┌────────────┤
     │                  R̃<1         R̃=1
     │                 代理失败       代理全通过
     │                   │             │
     │             V锁定→修复S         ▼
     └──────────────┘         GT Oracle(仅返回pass/fail)
                                  │          │
                               pass        fail
                              部署S*     V升级→重评
#+end_example

路径一（代理测试失败）：验证器给出结构化诊断——哪些断言失败、根因是什么、怎么改。生成器据此修复技能，验证器测试套件锁定不变，逼生成器在同一组测试下过关。

路径二（代理测试全通过）：交给 Ground Truth Oracle 在全新环境中重跑，只返回一个不透明的 pass/fail 位，不透露任何测试内容。
如果 Oracle 失败，说明验证器的测试太松了——验证器被迫升级测试（更多、更难、更全面的断言），然后重新评估同一个技能。

这个信息隔离设计是关键：生成器永远看不到真值测试内容，只从不透明信号知道「你还没过关」；验证器也看不到生成器的推理过程，只从产出物和任务描述推断该测什么。
两者各自独立进化，靠 Oracle 的二值信号校准。

**消融证据**：去掉验证器但保留 5 轮进化（生成器只拿不透明 pass/fail），通过率从 71.1% 暴跌到 41.1%（−30pp）。生成器知道「失败」但不知道「为什么失败」，无法做定向修复。
反过来，只给背景上下文不做进化，是 42.4%——上下文提供了有用的基质，但协同进化才把它转化为结构化、经过验证的技能包。

**进化动态证据**：Round 0（一次性生成，无验证）≈ 32%，跟无技能基线持平。一旦验证环启动，Round 2 达到 44%，Round 3 超过人类手写技能（63% vs 53.5%），
Round 5 收敛到 75%。生成提示词在 Round 0 已经全部给出了——后续 43 个百分点的提升全部来自验证环。

这些结果在 SkillsBench 的 85 个任务上测得，使用 Claude Opus 4.6 和 GPT-5.2 作为进化骨干。跨模型迁移的增益（+35–44pp，覆盖 5 家公司的 6 个模型）说明技能编码的是可复用任务结构而非模型特定产物。
但最弱的模型（Mistral Large 3，基线 4.9%）即使加技能也只有 43.1%——技能不能弥补模型本身能力的严重不足。

系外行星检测的案例最能说明协同进化的价值。Agent 用 BLS 算法调参三轮都卡在 GT Oracle 的 75%（精度不够），
最终换成 TLS 算法才到 100%。「换算法」这个决定是 Oracle 的不透明 75% 反馈驱动的——验证器的功能测试发现不了 BLS 的精度天花板，
因为验证器自己也在用 BLS 交叉验证，甚至把自己的估计误差（0.00002 天）误判为 agent 的错误。验证器有用但有上限，GT Oracle 不可替代，两者缺一不可。

* 我能带走什么

以后构建 agent 技能时，先不急着判断「生成质量够不够好」，而先问「有没有一个独立于生成器的验证回路在持续施压——它能在代理自己认为通过时，用真值信号戳破假象并强制验证器升级测试？」

一个相关用法：在 agent 自改进系统中，把「改进者」和「评判者」放在不同会话、信息隔离，不是安全冗余而是质量必需——共享上下文会让评判者继承生成器的盲点，两人都看不见同一类错误。
