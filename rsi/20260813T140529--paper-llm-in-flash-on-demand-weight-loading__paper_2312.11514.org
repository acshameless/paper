#+title:      模型放不下内存时，瓶颈是闪存读取方式不是容量
#+subtitle:   LLM in a Flash: Efficient Large Language Model Inference with Limited Memory
#+source:     https://arxiv.org/abs/2312.11514
#+authors:    Keivan Alizadeh, Iman Mirzadeh, Dmitry Belenko, S. Karen Khatamifard, Minsik Cho, Carlo C Del Mundo, Mohammad Rastegari, Mehrdad Farajtabar

* 速读

手机上跑 7B 模型需要 14GB 内存，但手机 DRAM 只有几 GB——模型放不下。标准做法是量化压缩，但只是把问题从「放不下」变成「勉强放下」，没有改变「整个模型必须常驻内存」这个前提。
作者换了一个前提：模型存在闪存里，推理时只把当前 token 需要的那几个神经元权重搬进 DRAM。FFN 层有 90%+ 的激活稀疏——每步只有不到 10% 的神经元被激活，其余全是死重。
用一个轻量预测器提前算出哪些神经元会被激活，只搬这些，再配合滑窗复用和行列捆绑增大读取块，就能在 DRAM 只有模型一半大时跑推理，速度比朴素按需加载快 4-5 倍（CPU）到 20 倍（GPU）。

* 它到底在解决什么

一个 7B 参数模型，半精度下要 14GB 内存。大多数手机的 DRAM 远不够这个数。量化到 4-bit 能压到 3.5GB，但量化有精度损失，而且只是延缓问题——模型再大一点照样放不下。

根本前提是「整个模型必须常驻 DRAM」。但作者注意到一个事实：
FFN 层的 ReLU 激活有 90%+ 的稀疏率——每个 token 只激活不到 10% 的中间神经元。也就是说，每步推理中 90% 的 FFN 权重根本没被用到，却白白占着内存。

那把模型存在闪存里、按需读取呢？朴素做法是每步推理都从闪存加载需要的权重。但闪存随机读取极慢——小块随机读的吞吐只有 1.25 GB/s，而顺序大块读能到 6.1 GB/s。
朴素按需加载的延迟高达 2196ms/token，完全不可用。

问题变成了：怎么让「按需从闪存读权重」快到可用？

* 它真正看见了什么

瓶颈不在闪存容量，在读取方式——闪存对小而散的随机读取惩罚极重，对大而连续的顺序读取则快得多。

三个技术分别攻击延迟的三个来源：

关键机制是激活预测器：一个小型低秩网络（d_model → r → d_ffn），输入当前层的 attention 输出，预测哪些中间神经元会被 ReLU 激活。
预测器只需当前层的信息，不需要等上一层 FFN——这个延迟对按需加载至关重要，因为你可以提前知道要读哪些权重。预测器对零样本准确率几乎没有影响（ARC Easy: 66.1→66.2）。

滑窗技术利用了一个经验观察：相邻 token 激活的神经元高度重叠。处理新 token 时，只需加载与上一个窗口不同的那部分权重——而聚合使用率随窗口增大递减，所以窗口越大，每步增量传输越少。

配置                    传输量    吞吐       I/O 延迟
────────────────────────────────────────────────────
朴素（全量加载）         13.4 GB   6.1 GB/s   2196 ms

+预测器                  0.9 GB    1.25 GB/s   738 ms

+行列捆绑                0.2 GB    2.25 GB/s    87 ms
#+end_example

从 2196ms 到 87ms，25 倍改善。核心不是某个单一技术，而是三个技术叠在一起：预测器把传输量砍到 3%，滑窗再砍到 0.3%，捆绑把碎读变成块读把吞吐拉回 2.25 GB/s。

端到端延迟上，OPT 6.7B 在 CPU 上从 3182ms 降到 669ms（4.8x），GPU 上从 2218ms 降到 84ms（26x）。GPU 加速更显著是因为 GPU 计算快，I/O 占比更大，优化 I/O 的收益更明显。

这些结果在 DRAM 约为模型一半大小的条件下成立。论文也展示了内存-延迟的 trade-off 曲线：给更多 DRAM（窗口更大），传输更少，延迟更低。这是一个可调旋钮，不是非此即彼。

适用边界：当前只验证了单 batch 推理；功耗分析显示稀疏模型虽然瞬时功率更低，但因为推理时间更长，总能耗反而更高——这对手机电池是真实约束。预测器依赖 ReLU 激活稀疏，对非稀疏模型需要先做稀疏化（如 FATReLU 微调）。

* 我能带走什么

以后看到「模型放不下内存」的问题，先不急着量化压缩或换小模型，而先问：每步推理真正用到的权重占多少？如果 FFN 有 90% 稀疏，那 90% 的内存占用是死重——问题不是内存不够，是加载策略把死重和活重一视同仁。

但用这条路之前，先量一下闪存的随机读取吞吐：如果小块随机读只有 1 GB/s，按需加载必须配合块捆绑和滑窗才可用，否则朴素按需加载比全量加载更慢。
