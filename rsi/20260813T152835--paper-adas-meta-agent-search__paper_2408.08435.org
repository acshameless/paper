#+subtitle:   Automated Design of Agentic Systems (ADAS) / Meta Agent Search
#+source:     https://arxiv.org/abs/2408.08435
#+authors:    Shengran Hu, Cong Lu, Jeff Clune
#+venue:      ICLR 2025

* 速读

手工拼装 agent 的各个模块（思维链、自我反思、工具调用……）就像深度学习之前手工设计图像特征——有效但天花板低、搜索空间远非人力可穷尽。
这篇论文把整个 agent 系统定义成一段 Python 代码，让一个 meta agent 不断在代码空间里编程出新的 agent，测一测、好的存进档案，下一轮站在前面发现的基础上继续创新。
在阅读理解、数学、ARC 逻辑推理等任务上，自动搜出来的 agent 全面超过人类手工设计的最强 baseline，而且从数学域迁移到阅读理解域、从 GPT-3.5 迁移到 Claude-Sonnet 后仍然领先。
以后看到一套精心设计的 agent 架构，不该只问"设计得好不好"，而要先问"它能不能被自动搜索发现甚至超越"。

* 它到底在解决什么

一个具体的困惑：研究者花大量精力手工拼装 agent——先加思维链（Chain-of-Thought），再叠自我反思（Self-Refine），再挂工具调用，调 prompt、调流程、调角色分配。
每篇论文贡献一个新模块，但怎么组合它们几乎全靠直觉和试错。组合爆炸是显而易见的：光 prompt 和工作流两个维度，可能的搭配就远超人力能探索的范围。

原来的处理方式是手工设计：研究者提出一个新模块，在几个 benchmark 上验证有效，发表。这和深度学习之前计算机视觉领域手工设计 HOG、SIFT 等特征提取器的情况如出一辙。
机器学习的历史反复证明，手工设计最终会被学习到的方案取代——CNN 取代了 HOG，神经架构搜索取代了手工网络设计，学习到的损失函数超过了手工设计的 DPO。

但 agent 系统的设计自动化面临一个特殊困难：agent 的设计空间不像神经网络那样是连续参数，它是离散的、结构化的——用什么 prompt、调什么工具、按什么流程走，这些选择很难用梯度优化。
已有的自动 prompt 优化方法（如 OPRO、PromptBreeder）只改 prompt 文本，工作流等其余部分固定不变，搜索空间太窄。把 agent 表示成图或网络的方法则受限于预定义的节点和边类型，且搜索空间对模型不友好。

读者到这里会开始期待：有没有一种表示方式，既能覆盖所有可能的 agent 设计，又能让擅长写代码的大模型高效搜索？

* 它真正看见了什么

核心判断：把整个 agent 系统写成一段 Python 函数，搜索空间就变成图灵完备的代码空间——理论上任何可能的 agent 设计（任何 prompt、任何工具组合、任何工作流）都能被表示和发现。而大模型恰好擅长写代码，这让代码搜索成为对模型最友好的搜索空间。

Meta Agent Search 的机制很直接：一个 meta agent（用 GPT-4）反复编程新的 agent。每轮它读档案里已有的 agent 和分数，想一个"有趣的新设计"，写成代码，自反思确认新颖性，在验证集上测试，出错了就自我修正（最多 5 次），然后把结果存入档案。下一轮站在所有前人发现的基础上继续。

#+begin_example
  Meta Agent (GPT-4)
    │
    ├─ 1. 读 Archive（已发现 agent 代码 + 分数）
    ├─ 2. 生成新 agent：描述 + forward() 函数代码
    ├─ 3. 自反思：是否新颖？ → 否则修改
    ├─ 4. 验证集评估
    │     └─ 报错？→ 自反思修正（最多 5 轮）
    ├─ 5. 连同分数加入 Archive
    └─ 回到 1，直到迭代上限
#+end_example

meta agent 只需写一个 =forward()= 函数：输入任务信息，输出 agent 的回答。框架提供查询大模型、格式化 prompt 等基础函数，其余全交给 meta agent 自由发挥。这和 FunSearch 让模型写算法函数的思路一脉相承。

证据一：在四个 benchmark 上，自动搜索的 agent 全面超过所有手工设计的 baseline。差距最明显的是阅读理解（DROP，F1 从 65.8 提到 79.4，+13.6）和数学（MGSM，准确率从 39.0% 提到 53.4%，+14.4%）。
在知识和科学问答上差距较小——论文推测是因为这些任务更依赖模型本身的知识储备，agent 架构的优化空间有限。这个推测合理：当模型"不知道"答案时，再好的工作流也变不出知识。

证据二：在数学域搜出来的 agent，迁移到数学以外的阅读理解任务上仍然超过所有手工 baseline。更惊人的是，用 GPT-3.5 搜出来的 agent 迁移到 Claude-Sonnet 上，在 ARC 上达到 48.3% 准确率，而最强手工 baseline 只有 39.3%。
这说明搜出来的不是针对某个模型或某个域的 trick，而是有一定通用性的设计模式。

一个值得注意的观察：在 ARC 上，最终最好的 agent 并非突然出现，而是三个"垫脚石"逐步积累的结果——第 5 轮出现"多样化反馈"的想法，第 11 轮出现"用专家角色评估不同维度"，第 12 轮出现"模拟人类反馈"，最终最好的 agent 把三者融合。
这和进化算法中的交叉重组很像：单独的垫脚石性能不一定高，但后续设计能站在它们肩膀上。

这些结果较稳地显示了：代码空间的 agent 搜索不仅能超过手工设计，还能发现可迁移的设计模式。
但需要说明边界：实验只在单步问答任务上做，没有测试多步交互的复杂场景；搜索算法本身很朴素（只鼓励"有趣的新设计"），没有显式的探索-利用平衡；只优化了性能一个目标，没考虑成本和延迟。

* 我能带走什么

以后看到一套精心设计的 agent 架构，我先不急着判断"这个设计好不好"，而会先问：这个设计里的哪些部分是真正不可替代的，哪些只是搜索空间太窄时的手工近似？如果把它放进代码搜索里，自动搜索能不能发现同样的模式甚至更好的？

一个直接相关的用法：当你需要为某个新任务定制 agent 时，与其手工拼模块调 prompt，不如先跑几轮 Meta Agent Search——成本不高（不需要 GPU，只需 API 调用），但可能搜出你没想到的设计。
另一个用法：把搜出来的 agent 当作"诊断镜"——论文发现 GPT-3.5 搜出来的最优 agent 用了复杂反馈机制，但换到更强的 Claude-Sonnet 上，简单反馈加更多迭代反而更好。
这说明弱模型需要复杂架构补偿自身不足，强模型则受益于简洁。你选择 agent 架构时，也该先问：我的模型够强吗？它需要的是更复杂的脚手架，还是更多次简单迭代？
