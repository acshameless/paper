* 速读

Schmidhuber 的 Gödel Machine 设想了一个能自我改进的 AI，但要求每次改动都「形式化证明有益」——这在复杂系统里几乎不可能。
Darwin Gödel Machine（DGM）把这个证明要求换成「跑一遍 benchmark 看效果」，同时维护一个存档保留所有变体而非只留最好的那个。
结果：一个只有 Bash 和编辑工具的简单 coding agent，经过 80 轮自我修改，在 SWE-bench 上从 20% 涨到 50%，追平人类精心设计的开源方案。
关键判断变了：自改进不需要先证明有益，试错加存档就够；而且路径不是单调上升的——存档里那些暂时更差的变体，往往是后续突破的跳板。

* 它到底在解决什么

一个能自己改自己代码的 AI——Schmidhuber 2007 年就设想了，叫 Gödel Machine。它的规则很简单：每次改自己之前，先形式化证明这次改动「净有益」。证明通过才改，否则不动。
理论上完美，实践中几乎不可能：你怎么证明给一个 LLM coding agent 加一个代码搜索工具一定有益？效果取决于模型的训练数据、任务上下文、和其他工具的交互——这些你无法在改之前算清楚。

另一条路是 meta-learning（如 ADAS）：用一个固定的 meta-agent 去生成和优化下游 agent。问题是 meta-agent 自己不改进——它生成更好的下游 agent，但自己生成 agent 的能力没有因此变强。自指的环没有闭合。

DGM 要解决的就是这个：让一个系统既解决下游任务（写代码），又改进自己的代码，而且下游能力的提升直接意味着自改进能力的提升——因为自改进本身就是改代码，就是 coding 任务。

* 它真正看见了什么

新判断：自改进不需要形式化证明，用 benchmark 经验验证就够；但光有验证还不够，还必须保留所有变体的存档，否则一次坏修改就会卡死在局部最优。

DGM 的运转是一个循环：

#+begin_example
  ┌──────────┐  选父代   ┌────────┐  评测   ┌──────────┐
  │  存档    │─────────▶│自我修改│───────▶│benchmark │
  │ (所有    │ 性能+探索 │改自己  │ 能编译  │          │
  │  变体)   │          │代码库  │ 才入库  └────┬─────┘
  └────▲─────┘          └────────┘              │
       │                                         │
       └─────────────────────────────────────────┘
#+end_example

每一轮：从存档里选一个父代（性能越高越可能被选，但已有子代越少也越可能被选——兼顾利用和探索），父代分析自己的评测日志，提出一个改进方向，在自己的代码里实现它，生成一个新 agent。
新 agent 在 benchmark 上评测，只要能编译且保留编辑代码的基本能力就入库。80 轮后，存档长成一棵树。

两个设计选择缺一不可：

1. *经验验证替代形式证明*——不证明有益，跑一遍看分数。这让自改进在实践中可行。
2. *存档替代只留最新*——不只保留当前最好的，而是保留所有变体。这让探索能从任何变体分支出去。

为什么存档重要？因为改进路径不是单调上升的。论文的存档树（Figure 3）显示：最终最佳 agent 的谱系里有两个性能下降的节点——如果只留最新版本，这些路径会被丢弃，后续突破就不会发生。
一个叫 node 24 的关键创新引发了大量后续创新，而它本身不是当时最强的。

证据：

- *SWE-bench 从 20.0% 到 50.0%*，追平人类设计的开源 SoTA（51.0%）。Polyglot 从 14.2% 到 30.7%，远超人类开发一年的 Aider。这较稳地显示了经验验证 + 存档能让自改进持续生效。
- *去掉自改进*（meta-agent 固定不变）：早期有提升，但很快衰减——因为生成 agent 的能力本身没有在进步。
- *去掉开放式探索*（只留最新版本）：一次差的自我修改让后续改进更难——因为只能从那个差的版本继续。
- *跨模型、跨 benchmark、跨语言迁移*：在 SWE-bench 上搜出来的 agent 换到 Claude 3.7 上跑，从 19% 涨到约 59%；换到 Polyglot 上跑，从 14.2% 涨到 28.9%。这说明发现的是通用技能，不是过拟合。

DGM 自动发现的功能包括：更细粒度的文件查看（按行而非整文件）和编辑（按字符串替换）、多次生成 patch 并排序、参考历史尝试、上下文超限时自动摘要、patch 有效性验证与重试。
这些都是人类 coding agent 设计者会做的，但 DGM 自己发现了它们。

这最多说明：在 coding agent 的工具和工作流层面，经验验证 + 开放式探索能让自改进持续生效。它还没有改基础模型本身（只改 agent 代码），开放式探索过程本身也是固定的（不能被 DGM 修改），而且单次运行需要约两周和大量 API 费用。
关键假设是 coding benchmark 性能反映自改进能力——因为自改进就是改代码。

* 我能带走什么

以后看到「自改进系统需要证明每次改动有益」，先不急着判断「那不可能所以放弃」，而先问：能不能用经验测试替代证明？如果能，再问：只留最优解够不够，还是需要保留变体存档来避免卡死？

一个更具体的用法：在设计任何迭代优化系统时（不限于 AI agent），如果路径可能不是单调上升的，保留所有中间变体比只留当前最优更可能找到突破——因为暂时更差的变体可能是后续创新的跳板。
