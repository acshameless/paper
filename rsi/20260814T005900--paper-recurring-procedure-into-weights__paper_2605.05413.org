#+title:      反复流程进权重，只留状态在提示词
#+subtitle:   From History to State: Constant-Context Skill Learning for LLM Agents
#+source:     https://arxiv.org/abs/2605.05413
#+authors:    Haoyang Xie, Xinyuan Wang, Yancheng Wang, Puda Zhao, Feng Ju

* 速读

个人助手 agent 每次执行同一个工作流时，都要在提示词里重读完整的技能描述和不断增长的执行历史——做了 100 遍的事，每次仍从头读说明。
这篇论文把可复用的流程知识从提示词搬进轻量级任务族 LoRA 模块（权重），推理时只保留当前观察、一步上下文和一个确定性追踪器渲染的紧凑状态块，使上下文大小恒定、不随步数增长。
在 ALFWorld、WebShop、SciWorld 三个基准上，性能追平或超过已发表的 agent 训练方法，同时每轮提示词 token 减少 2-7 倍。核心判断：为反复执行的工作流设计 agent 时，要把"可复用流程"和"步内状态"分开——前者进权重，后者留提示词。

* 它到底在解决什么

一个个人助手 agent 每天通过同一个网页界面购物。每次执行时，它都要在提示词里重读完整的购物流程说明、技能描述，以及之前所有步骤的观察和动作记录。执行了 100 次之后，它仍然从头读同一份说明——练习从未变成策略的一部分。

当前做法把这个问题当作上下文管理来处理。ReAct 风格的 agent 在提示词里重放历史观察、动作和推理轨迹；记忆增强型 agent 把过去交互存储、摘要、检索后放回提示词。
但即使记忆 agent 也只是减少了历史长度，可复用的流程知识仍然以文本形式存在于提示词中，每次推理都要重新选择和处理。上下文长度随步数线性增长：

#+begin_example
|c_hist_t| ≈ |g| + |d_k| + Σ(|o_i| + |a_i|)
#+end_example

其中 =d_k= 是技能描述、示例等任务族上下文，每步都要重新处理。对于反复执行的工作流，这是浪费——agent 反复读它已经会做的流程，而不是把练习固化进策略。

* 它真正看见了什么

对于反复执行的工作流，可复用的流程知识应该存在模型权重里，而不是提示词里。提示词只携带每步变化的信息。

具体做法：为每个任务族在冻结的基础模型上训练一个轻量 LoRA 模块 =φ_k= ，让模块内化流程。
推理时，agent 只看一个恒定大小的输入：任务目标 + 当前观察 + 一步上下文（上一步的观察和动作）+ 紧凑状态块。一个确定性追踪器 =M_k= （不是 LLM）从动作和观察更新结构化状态，
并渲染状态块——只包含下一步决策需要的字段，如当前子目标、已获取的物体、已检查的位置、剩余要求等。

关键结构是追踪器的双重角色：它既为模型渲染状态块（推理时），又从同一组追踪字段生成子目标奖励（训练时）。这使得 RL 精炼强化的是策略对状态块的使用，而非对历史轨迹的记忆。

#+begin_example
旧: c_t = g + d_k + h_t        (随步数增长, 每步重读)
                               新: x_t = g + o_t + q_t + b_t  (恒定, 不随步数增长)
                                      ↑
                           ┌── 确定性追踪器 M_k ──┐
                           │                      │
                     渲染状态块 b_t          子目标奖励 r_prog
                     (推理: 给模型看)        (训练: 给RL用)
                           │                      │
                           └── 同一组追踪字段 ─────┘
#+end_example

训练分两阶段：先用专家轨迹做步级 SFT，再用 GRPO 风格的在线 RL 精炼。RL 奖励 =r_env + r_prog - r_err= 中的进度项和惩罚项都围绕追踪器的子目标字段定义，推理时无需任何 LLM 裁判。

证据一：性能不因上下文缩减而牺牲。Qwen3-8B 的 SFT+RL 在 ALFWorld unseen 达 89.6%、WebShop 76.8%、SciWorld unseen 66.4%，追平或超过已发表方法（GiGPO 90.8% ALFWorld，EMPO2 76.9% WebShop / 75.9 SciWorld）。
三个不同骨干模型（Qwen3-4B、Qwen3-8B、Llama-3.1-8B）均受益于同一训练方案，说明增益来自任务族训练设计而非特定预训练模型。这较稳地显示：恒定上下文不牺牲能力。

证据二：上下文效率。相比 ReAct-full，每轮提示词 token 在 ALFWorld 从 1.3k 降到 0.18k，WebShop 从 3.1k 降到 0.49k；单集总 token 在 ALFWorld 从 34k 降到 3k。消融实验（WebShop, Qwen3-8B）显示各组件的递进贡献：

#+begin_example
仅当前观察           1.2% 成功率
+ 一步上下文          5.6%
+ 状态块             23.6%   ← 提示词侧关键信号
+ SFT               62.2%   ← 流程搬进权重
+ RL                 76.8%   ← 在线精炼
#+end_example

状态块是提示词侧的主要信号（从 5.6% 跳到 23.6%），SFT 把可复用流程搬进权重（从 23.6% 到 62.2%），RL 进一步精炼。去掉状态块后训练好的模型成功率下降 15.6 个百分点，说明模型确实在用状态块作为执行状态，而非记忆固定轨迹。

适用边界：追踪器和奖励规则是任务族级别的，需要人工设计（GPT-5.5 离线辅助起草，但仍需验证）。仅在文本模式环境测试，未覆盖 GUI 和多模态。新技能需要训练新适配器，不能零样本迁移——但每个适配器仅 0.5-0.7 GB，推理时只加载当前一个。

* 我能带走什么

以后为反复执行的工作流设计 agent 时，先问一个问题：提示词里的信息是可复用流程（每次都读同一份说明），还是步内状态（每步都不同）？如果 agent 每次都重读同样的指令，这说明流程知识该进权重，不该留在上下文。

一个相关用法：判断现有 agent 的上下文成本是否合理——如果大部分 token 在重复处理固定流程描述而非步内状态，就是搬进权重的候选。
另一个用法：设计新 agent 时，先确定哪些信息是"每步变化的"（留提示词），哪些是"每次执行都一样的"（进权重），再决定是否需要确定性追踪器来压缩中间状态。
