#+title:      优化LLM外壳，原始轨迹胜过压缩分数
#+subtitle:   Meta-Harness: End-to-End Optimization of Model Harnesses
#+source:     https://arxiv.org/abs/2603.28052
#+authors:    Yoonho Lee, Roshen Nair, Qizheng Zhang, Kangwook Lee, Omar Khattab, Chelsea Finn

* 速读

LLM 系统的性能不只取决于模型权重，还取决于"外壳"（harness）——那层决定存什么、取什么、给模型看什么的代码。但外壳至今靠手工调，而现成的文本优化器把反馈压成标量分数或短摘要，丢掉了追踪失败因果链所需的诊断信息。
Meta-Harness 让一个编码智能体通过文件系统访问所有先前候选的源码、执行轨迹和分数，自己决定看什么、改什么。
消融实验显示：只给分数时中位准确率 34.6%，加摘要 34.9%，而给原始执行轨迹跳到 50.0——摘要不仅没救回来，还可能压缩掉了诊断关键。
以后优化复杂 LLM 系统时，别急着把反馈压成分数，先问：优化器能不能看到失败发生在哪一步、由哪个设计选择引起。

* 它到底在解决什么

同一个模型、同一个 benchmark，只换外壳就能产生 6 倍的性能差距。外壳——决定 LLM 在每一步看到什么上下文的代码——和模型权重一样重要。但外壳工程仍然是手工活：工程师看失败案例、调启发式规则、迭代少数几个设计。

一个自然的想法是用现成的文本优化器自动搜索。但这些方法在 harness 工程里水土不服，因为它们把反馈压得太狠：有的只看当前候选，有的只条件于标量分数，有的把反馈限制在短模板或 LLM 摘要里。
在它们研究的场景中，每步优化可用的上下文只有 100 到 30000 token；而一次 harness 评估能产生多达一千万 token 的诊断信息——差了三个数量级。

这不是"压缩一下也够用"的工程取舍。外壳是有状态程序：一个关于存什么、何时取、怎么展示的选择，可能在很多步推理之后才暴露后果。压缩反馈往往恰好删掉了把下游失败追溯到上游设计选择所需的信息。

* 它真正看见了什么

新判断：harness 优化不需要更聪明的搜索结构，而需要让优化器选择性访问完整的先前经验——原始代码、执行轨迹和分数——由优化器自己决定看什么。

Meta-Harness 的机制极简：一个编码智能体（Claude Code）面对一个不断增长的文件系统，里面存着每个先前候选的源码、分数和执行轨迹。它用 grep 和 cat 按需检索，而不是把所有历史塞进一个 prompt。
每轮它先检查先前的代码和轨迹，推理失败原因，再写新 harness。没有固定的父选择规则，没有预定义的变异算子——诊断和编辑决策全部交给编码智能体。

关键证据是消融实验（Table 3）。在在线文本分类上，三种条件对比：

#+begin_example
反馈条件              中位准确率  最佳准确率
只有分数              34.6        41.3
分数 + LLM 摘要       34.9        38.7
分数 + 原始轨迹(完整)  50.0        56.7
#+end_example

摘要不仅没挽回信号，中位准确率甚至比纯分数还低——压缩掉了诊断细节。完整轨迹的中位候选就超过了两种压缩条件下的最佳候选。这较稳地显示：访问原始执行轨迹是 harness 搜索最关键的成分。

第二个证据来自搜索轨迹本身。在 TerminalBench-2 搜索中，前两轮候选都把结构性修复和 prompt 模板改动打包在一起，都大幅回退。第三轮，proposer 自己诊断出回退的共因是共享的 prompt 改动而非结构修复，隔离出结构修复单独测试。
到第七轮，它在六连退后转向纯加性修改（在 agent 循环开始前注入环境快照），成为本轮最佳。这种跨候选的因果推理——识别混淆、隔离变量、从失败中学习——正是压缩反馈优化器做不到的。

这些结果在三个领域一致：
在线文本分类上比最强手工 harness（ACE）高 7.7 分且用 4 倍更少的上下文 token；
在 IMO 级数学推理上，单个发现的检索 harness 跨五个未见模型平均提升 4.7 分；
在 TerminalBench-2 上，自动发现的 harness 在 Haiku 4.5 组排第一、Opus 4.6 组排第二。

适用边界：这些结果是在一个特别强的编码智能体（Claude Code / Opus 4.6）上获得的。论文承认 proposer 能力对效果的影响尚未系统研究。
TerminalBench-2 上搜索和评测在同一 benchmark 上进行（虽然做了过拟合审计），这是该 benchmark 的标准做法但仍是局限。
文本分类是最小上下文场景——如果结构密集的优化器在这里已经落后，更难场景下差距可能更大，但这只是推断。

* 我能带走什么

以后看到"用标量分数或短摘要做反馈来优化复杂 LLM 系统"，先不急着判断"搜索结构够不够好"，而先问：优化器能不能看到失败发生在哪一步、由哪个设计选择引起？如果反馈被压缩到丢失了因果链，换更聪明的搜索算法也补不回来。

一个直接用法：当你需要优化一个有状态的 LLM pipeline（检索策略、记忆管理、prompt 构建逻辑）时，把每次评估的完整执行轨迹存成文件，让编码智能体自己 grep 和 cat 来诊断——而不是手写反馈摘要或固定变异算子。
