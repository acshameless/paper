#+title:      模型能从自己的失败中改自己的外壳
#+subtitle:   Self-Harness: Harnesses That Improve Themselves
#+source:     https://arxiv.org/abs/2606.09498
#+authors:    Hangfan Zhang, Shao Zhang, Kangcong Li, Chen Zhang, Yang Chen, Yiqun Zhang, Lei Bai, Shuyue Hu
#+venue:      arXiv 2026 (Shanghai AI Laboratory)

* 速读

同一个模型，换个外壳（harness：系统提示、工具、运行时控制、验证规则等），表现可以差一倍——但外壳至今靠人工为每个模型逐个调，模型越多越不可持续。
这篇论文让模型自己跑任务、从自己的失败轨迹中聚类出反复出现的失败模式，再针对每个模式提出最小修改，最后用回归测试只接受不退化的改动。
九个模型-benchmark 组合全部提升，而且不同模型自动得到完全不同的修改——说明执行轨迹里已经包含了足够的信息，让模型把自己的弱点变成外壳级的修复。

* 它到底在解决什么

一个具体困惑：Qwen3.5-35B-A3B 在 Terminal-Bench-2.0 上只有 18% 通过率，但换一个外壳就到 36.7%——模型没变，变的只是系统提示、工具配置和运行时规则。外壳对 agent 表现的影响和模型本身一样大。

但外壳设计是 model-specific 的手工活。不同模型有不同的失败习惯：MiniMax 忘了创建输出文件、Qwen 卡在重试循环里、GLM 跨 shell 命令丢环境变量。一个对 MiniMax 好用的外壳套在 Qwen 上可能更差。
新模型发布越来越快，人工为每个模型定制外壳越来越不可持续。

已有的自动化路线要么靠更强的外部 agent 来优化弱 agent 的外壳（Meta-Harness），要么把外壳设计当成外部搜索空间。但外部 agent 可能很贵、对前沿模型不可用、或者和目标模型的失败模式不匹配。
这篇论文问的是：能不能不靠外部力量，让模型自己改自己的外壳？

* 它真正看见了什么

新判断：模型自己跑任务产生的执行轨迹里已经包含了足够的信息，让同一个模型能把自己的反复失败模式变成有针对性的外壳修改——不需要更强的外部 agent，也不需要人工工程师。

最小机制是一个三阶段反馈回路：

#+begin_example
    ┌─────────────────────────────────────┐
    │  1. Weakness Mining                  │
    │  跑任务 → 聚类失败轨迹 →              │
    │  提取可复用失败模式                   │
    └──────────┬──────────────────────────┘
               │  evidence bundle
               ▼
    ┌─────────────────────────────────────┐
    │  2. Harness Proposal                 │
    │  同一模型针对每个失败模式              │
    │  生成 K 个最小修改候选                │
    └──────────┬──────────────────────────┘
               │  candidate edits
               ▼
    ┌─────────────────────────────────────┐
    │  3. Proposal Validation              │
    │  回归测试: held-in + held-out        │
    │  只接受不退化的修改 → 合并进外壳      │
    └──────────┬──────────────────────────┘
               │  updated harness h(t+1)
               │
               └──→ 回到第 1 步
#+end_example

关键设计选择有三处。
第一，失败聚类不是按表面症状（都叫 timeout），而是按"验证器拒绝的原因 + agent 侧行为 + 可复用机制"三元组签名来聚——两个 timeout 可能需要完全不同的修改。
第二，提议阶段要求每个修改绑定一个具体失败机制和一个具体可编辑面，不能泛泛地加指令。
第三，接受标准是保守的：held-in 和 held-out 都不能退化，只拿一个换另一个的修改直接拒绝。

两个证据改变判断：

第一，九个模型-benchmark 组合全部提升，包括从未给提议者看过的 held-out 任务。最大相对提升 132%（Qwen3.5 在 AppWorld 从 22.5% 到 52.2%），最大绝对提升 40.6 个百分点（GLM-5 在 AppWorld 从 44.4% 到 85.0%）。
held-out 也提升说明修改针对的是可复用执行机制，不是对 held-in 案例的过拟合。

第二，不同模型自动得到完全不同的修改。MiniMax 得到"尽早创建输出文件 + 50 次工具调用后强制转向"；Qwen 得到"依赖预检 + 循环打断 + 工具报错后恢复产物"；GLM 得到"跨 shell 持久化环境变量 + 从探索转向实现"。
同一个 benchmark、同一个初始外壳，三个模型各自走出了不同的改进路径——这正是 model-specific 改进的证据。

这些结果较稳地显示：在固定 benchmark、固定模型、固定评估器的条件下，把外壳当成可经验更新的状态，模型自己就能把它从粗糙推向更好。
但它还没有说明这种改进在开放环境中是否持续，接受标准仅靠 pass-rate 非退化，更高风险的修改（如重构控制架构）需要更强的门。

* 我能带走什么

以后看到 agent 表现差，先不急着换更强的模型，而先问：它的失败是模型能力不足，还是外壳缺少某个执行规则？
如果是反复出现的同类失败（总忘创建文件、总卡在循环里、总丢环境变量），那问题可能不在模型，而在外壳——而模型自己的轨迹已经告诉你该改什么。

一个相关用法：在部署 agent 时，与其人工写一个"万能"外壳，不如给一个最小外壳，让模型跑一轮、看失败模式、改一轮、回归测试一轮。外壳改进是经验状态转换，不是一次性设计。
