#+title:      更新 harness 的能力不等于用好 harness 的能力
#+subtitle:   Harness Updating Is Not Harness Benefit: Disentangling Evolution Capabilities in Self-Evolving LLM Agents
#+source:     https://arxiv.org/abs/2605.30621
#+authors:    Minhua Lin, Juncheng Wu, Zijun Wang, Zhan Shi, Yisi Sang, Bing He, Zewen Liu, Tianxin Wei, Zongyu Wu, Zhiwei Zhang, Dakuo Wang, Xiang Zhang, Benoit Dumoulin, Cihang Xie, Yuyin Zhou, Suhang Wang, Hanqing Lu

* 速读

LLM agent 的自演化（harness self-evolution）不更新模型权重，而是让一个"evolver"模型根据执行经验更新外部 harness（提示、技能、记忆、工具）。此前所有评测只问端到端涨了多少分，把涨分来源搅成一锅。
这篇把涨分拆成两种能力：*更新 harness 的能力*（evolver 侧）和*用好 harness 的能力*（agent 侧），再用 7 个模型 × 3 个 benchmark 交叉配对实验。
结果发现：更新能力与模型基础能力几乎无关——9B 模型写的技能和 Claude Opus 4.6 写的"过程同构"；而受益能力是非单调的——弱模型最该受益却受益最少，因为它们连 harness 都加载不进上下文，加载了也跟不住。
所以以后把算力花在 task-solving agent 上而非 evolver 上，并训练 agent 的 harness 调用和长程指令遵循。

* 它到底在解决什么

一个 9B 的开源模型（Qwen3.5-9B）和一个前沿模型（Claude Opus 4.6）分别给同一个 agent 写技能。写出来的技能步骤几乎一模一样，agent 用哪个都能把任务做对。
但换一个弱模型（Qwen3-32B）当 agent，同样的技能摆在面前，它连加载都加载不进来——技能加载率只有 25%，而强模型是 96%。

这个反常现象之所以重要，是因为当前所有自演化 agent 的评测都在问一个端到端问题："自演化涨分了吗？"涨了就好。但涨分可能来自三个方向：agent 本来就强、evolver 写的 harness 好、或者 agent 善于利用 harness。
这三个来源被搅在一起，导致系统设计者不知道该把预算花在哪——是花大钱买最强的 evolver，还是花在让 task-solving agent 更强？

* 它真正看见了什么

核心判断：*更新 harness 的能力和用好 harness 的能力是两种独立的能力，且都不随模型基础能力单调变化。*

**发现一：更新能力是"平"的。** 固定 agent、换 evolver，不同能力档位的模型产出的 harness 更新带来的增益惊人地接近。在任何 benchmark 上，最好和最差的 evolver 之间差距最多 3.1 个百分点。
没有哪个模型在所有 benchmark 上都赢。更关键的是，9B 模型在 SkillsBench 上甚至超过了 Opus 4.6。Case study 显示，9B 和 Opus 写出的技能是"过程同构"的——同样的步骤序列，只是措辞和长度不同。

**发现二：受益能力是"非单调"的。** 固定 evolver、换 agent，受益曲线呈倒 U 形：中档模型受益最大，强模型因天花板效应受益少，弱模型——尽管提升空间最大——受益却最少。

#+begin_example
  受益能力 (Δ_benefit)
       ^
       |        中档模型
       |         峰值
       |        /  \
       |       /    \  强模型
       |      /      \  (天花板)
       |  弱模型      \
       |  (加载/遵循失败)
       +-------------------> 基础能力
#+end_example

弱模型受益少不是天花板的缘故，而是两种失败模式：

#+begin_example
  弱模型的两种失败模式
  ┌─────────────────────────────────────────────┐
  │ (A) 激活失败            (B) 遵循失败          │
  │                                             │
  │  技能没进上下文          技能进了上下文       │
  │       ↓                       ↓             │
  │  Qwen3-32B 把加载请求    Qwen3-32B 把技能    │
  │  塞进多键 JSON，          当现成脚本跑，      │
  │  格式校验拒绝，           失败后直接放弃，     │
  │  技能体从未加载           不走 fallback chain  │
  │                             ↓               │
  │  加载率 25% vs 96%       遵循率 0.14 vs 0.76 │
  └─────────────────────────────────────────────┘
#+end_example

更关键的是，遵循能力随轨迹推进而衰减。Qwen3-32B 在加载后遵循率 0.52，到最终验证阶段跌到 0.13；Opus 4.6 从 0.89 只跌到 0.80。弱模型不是在加载时读错了 harness，而是在长程执行中逐渐丢失了对 harness 的遵循。

证据分寸：这些结论基于 3 个 benchmark、7 个模型的交叉配对，在多模型多任务且有反例控制的条件下较稳地显示。但模型集不穷尽，且只覆盖 harness 自演化（权重冻结），不涉及参数微调或混合适配。

* 我能带走什么

以后看到自演化 agent 的端到端涨分，先不急着判断"这个演化方法好"，而先问：涨分来自 evolver 写得好，还是 agent 用得好？如果只看到端到端数字，就拆开看两侧。

两个直接用法：
- 选 evolver 时，不必买最贵的模型。9B 开源模型就能写出和前沿模型过程同构的技能，evolver 侧的增益天花板很低（≤3.1pp）。
- 弱 agent 不受益时，先查加载率和遵循率，而不是怪 evolver 写得差。瓶颈大概率在 agent 侧的 harness 调用和长程指令遵循。
