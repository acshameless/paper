#+title:      模型给自己当裁判，就能改好自己的输出
#+subtitle:   SELF-REFINE: Iterative Refinement with Self-Feedback — 同一个 LLM 生成、审查、修改自己的输出，无需额外训练
#+source:     https://arxiv.org/abs/2303.17651
#+authors:    Aman Madaan, Niket Tandon, Prakhar Gupta, Skyler Hallinan, Luyu Gao, Sarah Wiegreffe, Uri Alon, Nouha Dziri, Shrimai Prabhumoye, Yiming Yang, Shashank Gupta, Bodhisattwa Prasad Majumder, Katherine Hermann, Sean Welleck, Amir Yazdanbakhsh, Peter Clark

* 速读

LLM 一次生成常常不够好——对话回复不够生动、代码能跑但太慢、约束生成漏了关键词。传统做法是训练一个专门的"修改器"模型，成本高且需要领域数据。
这篇论文发现：同一个 LLM 就能充当自己的裁判和修改器——先生成初稿，再给自己写反馈（"这里用了暴力枚举，应该用公式 n(n+1)/2"），然后根据反馈改稿，反复迭代。
关键不在"多生成几次"，而在反馈必须具体可操作。在 7 个任务上平均提升约 20 个百分点，但数学推理几乎没提升——因为模型看不出自己哪里算错了。这说明自反馈的天花板不在于"会不会改"，而在于"能不能看出问题"。

* 它到底在解决什么

想象一个场景：你让 GPT-4 写一段 Python 代码计算 1 到 N 的和。它给你：

#+begin_src python
def sum(n):
    res = 0
    for i in range(n+1):
        res += i
    return res
#+end_src

代码能跑，但用了暴力循环。你心里清楚有更好的写法，但模型这一次没给你。

再想象另一个场景：你让模型写一段对话回复，用户说"我想打乒乓球"。模型回复"这很好，可以社交和锻炼"——没有错，但很无聊，没有和用户建立连接。

这两个场景的共同点是：模型的第一次输出不是"错的"，而是"不够好的"。问题出在多维度的质量要求上——代码既要正确又要高效，对话回复既要相关又要生动又要安全。一次生成很难同时命中所有维度。

人们原来的做法分两条路：一是接受第一次输出，凑合用；二是训练一个专门的 refinement 模型来改进输出。
但第二条路需要领域相关的训练数据，或者需要昂贵的人类标注来训练奖励模型（reinforcement learning from human feedback, RLHF）。每换一个任务就得重新训练，成本高且不灵活。

于是问题变成了：那个生成输出的模型，能不能自己看出哪里不够好，然后自己改？如果可以，就完全不需要额外训练。

* 它真正看见了什么

核心发现：一个足够强的 LLM 可以同时扮演三个角色——生成者、裁判、修改者——只要反馈是具体且可操作的（actionable and specific），不是"让它更好"这种废话，而是"这段代码慢是因为用了六层嵌套循环，应该用动态规划"这种能直接照着改的诊断。

机制很简单，是一个反馈回路：

#+begin_example
    ┌───────────┐
    │  生成初稿  │ y_0 = M(prompt_gen, x)
    └─────┬─────┘
          │
    ┌─────▼─────┐
    │  自我反馈  │ fb = M(prompt_fb, x, y_t)
    │  "哪不好   │   同一个模型，用 few-shot 示例
    │  怎么改"   │   教它写出具体可操作的反馈
    └─────┬─────┘
          │
    ┌─────▼─────┐
    │  自我修改  │ y_{t+1} = M(prompt_refine, x, y_t, fb)
    │  改完的稿  │   把所有历史反馈和修改都带在
    └─────┬─────┘   上下文里，避免重蹈覆辙
          │
    ┌─────▼─────┐
    │  该停了吗 │ ──"没停"──→ 回到「自我反馈」
    └─────┬─────┘
          │ "停了"（模型说不需要再改，或到最大轮数）
          ▼
       最终输出
#+end_example

三个 prompt（生成、反馈、修改）用 few-shot 示例定义，没有任何训练。同一个底层模型贯穿全程。最多迭代 4 轮。

这个回路能跑起来，最重要的条件是反馈的质量。论文做了一个关键的消融实验：

| 反馈类型 | 代码优化 | 情感反转 | 缩写生成 |
|---|---|---|---|
| 具体可操作的反馈（SELF-REFINE） | 27.5 | 43.2 | 56.4 |
| 泛泛的反馈（"提升代码效率"） | 26.0 | 31.2 | 54.0 |
| 没有反馈（只是反复说"改好一点"） | 24.8 | 0.0 | 48.0 |

情感反转任务最能说明问题：没有具体反馈时，模型完全无法改进（0 分）；泛泛的反馈能恢复一部分；只有具体指出"这段话只有一个正面词，要加更多负面词"才能达到 43.2。

另一个关键实验排除了"只是多生成几次"的解释：让模型直接生成 4 个独立输出，SELF-REFINE 的单个输出仍然被人类评委偏好于所有 4 个独立输出中的任何一个。这说明改进来自反馈驱动的修改，而非采样多样性。

在 7 个任务上的整体结果也较稳地支持了这个判断——GPT-4 的对话回复偏好率从 25.4% 提升到 74.6%（+49.2 个百分点），约束生成从 15% 提升到 45%（+30 个百分点），代码可读性从 27.4% 提升到 56.2%。
跨 GPT-3.5、ChatGPT、GPT-4 三个模型，提升趋势一致，且更强的模型（GPT-4）从 SELF-REFINE 中获益更大。

但有一个刺眼的例外：数学推理几乎零提升（GPT-4 从 92.9 到 93.1，+0.2）。原因不是模型不会改，而是模型看不出自己哪里错了——ChatGPT 在 94% 的数学题上给自己写的反馈是"一切看起来都很好"。
数学错误往往隐藏在某一步运算中，推理链表面上看起来连贯，模型就被骗了。

当论文给模型一个外部信号（Oracle Feedback，告诉它答案对不对）时，数学推理的提升立刻跳到 5% 以上。这个对照实验精确地定位了瓶颈：不是修改能力不足，而是自我诊断能力不足。

* 我能带走什么

以后看到 LLM 的输出"能用但不够好"时，先不急着换更大的模型或训练专门的修改器，而先问一个问题：**这个任务里，模型能不能自己看出哪里不好？**

如果能——比如对话是否生动、代码是否高效、是否覆盖了所有关键词——那自我反馈回路大概率有效，成本几乎为零。
如果不能——比如数学推理的中间步骤对不对——那瓶颈在错误诊断而非修改能力，需要引入外部验证信号（编译器、测试用例、答案校验），自我反馈帮不上忙。

一个相关的判断：多维度的、有明确质量标准的任务（生成要同时满足好几个条件）是 SELF-REFINE 的甜区，因为第一次生成容易顾此失彼，而反馈能逐个维度地补漏。单维度且错误隐蔽的任务（如数学推理）则是它的盲区。
