#+title:      自我改进的机制本身必须可编辑
#+subtitle:   HyperAgents: Self-Referential Agents for Open-Ended Improvement
#+source:     https://arxiv.org/abs/2603.19461
#+authors:    Jenny Zhang, Bingchen Zhao, Wannan Yang, Jakob Foerster, Jeff Clune, Minqi Jiang, Sam Devlin, Tatiana Shavrina
#+venue:      arXiv 2026 (FAIR at Meta / UBC / Vector Institute)

* 速读

自我改进系统（如 Darwin Gödel Machine）在编程领域有效，是因为"写代码的能力"和"修改自己代码的能力"天然对齐——改进一个就改进了另一个。
但一旦换到论文评审或机器人奖励设计，这种对齐就断了：固定的、手工编写的元级机制（负责生成自我改进指令的部分）是为编程定制的，出了编程就产出 0 分。
作者把 task agent 和 meta agent 合并成一个可编辑程序（hyperagent），让"负责改进的机制"本身也能被改进——这叫元认知自我修改（metacognitive self-modification）。
结果：在编程上追平专门为编程设计的 DGM，在非编程领域大幅超越手工定制的 DGM，而且元级改进能跨域迁移、跨轮次累积。

* 它到底在解决什么

Darwin Gödel Machine（DGM）是一个能自我改进的编程 agent：它不断生成自己的变体，在编程任务上评估，把好的变体存档作为未来改进的踏脚石。
它之所以在编程上有效，靠的是一个隐藏假设——评估任务（编程）和自我修改所需的技能是同一件事。你编程变强了，你修改自己的能力也变强了。

但这个假设在编程之外不成立。论文评审需要的是判断力和结构化决策流程，机器人奖励设计需要物理模拟器知识——这些技能和"修改 agent 代码"的技能完全不同。
DGM 的元级机制（一个固定的 prompt，负责分析历史表现并生成自我改进指令）是为编程手工写的，搬不动。实验直接验证了这一点：把原版 DGM 原封不动用在论文评审和机器人奖励设计上，测试得分都是 0.0。

你可以手动为每个新领域重新定制 DGM 的指令生成机制（论文叫 DGM-custom），但这等于每换一个领域就要人工重写一遍——自我改进的"自我"其实还是人在做。

问题的根源不是 DGM 的元级机制写得不好，而是它不可改。只要元级机制是固定的，系统的自我改进能力就被这个固定部件的天花板锁死。加一个 meta-meta 层来改进 meta 层只是把问题上移，导致无限回退。

* 它真正看见了什么

如果让元级机制本身可编辑，系统就能改进自己的改进过程，不再依赖任务技能与自我修改技能的对齐。

hyperagent 的做法是把 task agent（解决任务的程序）和 meta agent（生成新 agent 的程序）合并成一个可编辑的 Python 程序。
因为 Python 是图灵完备的，agent 可以编辑任何代码——包括负责生成改进的那段代码。这打破了"固定元级机制"的瓶颈：

#+begin_example
DGM:    [Task Agent] ←固定指令生成→ [改进]
         ↑ 同一个编程 agent，靠对齐假设

DGM-H:  [Task Agent + Meta Agent] = 一个可编辑程序
         ↑ meta agent 可以改自己 → 改进机制本身在进化
#+end_example

DGM-H 保留了 DGM 的开放式探索结构（维护一个 agent 档案库，通过分支、变异、评估来积累踏脚石），但把固定的指令生成换成了可编辑的 meta agent。
每次迭代，被选中的父 hyperagent 生成自己的修改版（可以改 task 部分，也可以改 meta 部分），评估后加入档案。

**证据一：编程上追平专用系统。** 在 Polyglot 编程基准上，DGM-H 从 0.140 提升到 0.340（训练集）/ 0.267（全量测试集），与原版 DGM（0.140→0.380 / 0.142→0.307）相当。
关键：DGM-H 没有为编程做任何手工定制，而 DGM 的指令生成机制是专门为编程写的。这说明可编辑的 meta agent 能自己找到不亚于手工设计的改进策略。

**证据二：非编程领域大幅超越。** 在论文评审上，DGM-H 从 0.0 提升到 0.710（测试集），超过开源静态基线 0.630；原版 DGM 是 0.0，手工定制的 DGM-custom 是 0.590。
在机器人奖励设计上，DGM-H 从 0.060 提升到 0.372，DGM-custom 是 0.348。消融实验显示：去掉自我改进（固定 meta agent）或去掉开放式探索（不维护档案库），性能都接近 0——两个组件缺一不可。

**证据三：元级改进可跨域迁移。** 这是最关键的发现。从论文评审+机器人奖励设计的 DGM-H 运行中取出一个 hyperagent，冻结其 meta agent，放到一个全新领域（IMO 数学竞赛评分）上，用 50 次迭代生成新 task agent。
结果：改进量（imp@50）从初始 agent 的 0.0 跃升到 0.630。同样实验用 DGM-custom 的迁移 agent，imp@50 仍是 0.0——DGM-custom 的改进是领域特定的，不迁移。
DGM-H 自主学会了性能追踪（PerformanceTracker）和持久记忆（persistent memory）等通用元级能力，这些能力不绑定任何特定领域。

这些结果在当前实验条件下成立：固定任务分布、固定外层循环（父选择和评估协议不可改）、80-200 次迭代规模。论文承认这些固定组件限制了完全的自我可修改性，附录 E.5 有初步实验探索让父选择机制也可改。
跨域迁移的统计显著性在 p<0.05 水平上成立，但跨轮次累积（Section 5.3）的差异未达统计显著（p>0.05），只是中位数和置信区间更高——这部分是提示性的，不是确证。

* 我能带走什么

以后看到一个"自我改进系统"，先不急着判断"它的任务表现变好了吗"，而要先问：**它改进自己的能力变好了吗？改进机制本身是固定的还是可编辑的？**

如果改进机制是固定的，那系统在编程上的成功可能只是靠"任务技能与自我修改技能恰好对齐"的运气——换个领域就会暴露。如果改进机制可编辑，但元级改进不能跨域迁移，那它可能只是学到了领域特定的优化技巧，而不是真正的元认知能力。

一个相关用法：评估 agent 框架时，看它改进的是 task agent 的 prompt/参数，还是连"怎么生成改进"的流程也在进化。前者是优化，后者才是自我改进的复利来源。
